# Glossário de domínio

Termos de domínio do habbo_r63b_v2. Mantenha o código e a conversa usando estes nomes.

## Protocolo

- **Era de protocolo (`ProtocolEra`)**: a família de wire/headers a que um cliente pertence, detectada **empiricamente no decoder** pelo framing dos primeiros bytes — o cliente pré-shuffle não reporta versão na conexão. Não confundir com a release string (`session.release`), que é só a chave de lookup das tabelas de header. Três eras:
  - **Wedgie pré-shuffle**: framing B64 delimitado (`@`), headers fixos. r34/2009-06-16 → **2011-08-14** (último build puro: `RELEASE63-35336-34886-201108141653`).
  - **Pré-shuffle moderno**: encoder moderno (int length + short header), headers ainda fixos. **2011-08-17** (primeiro: `RELEASE63-35436-34886-201108172310`) → **2011-10-04** (última estática: `RELEASE63-201110040910`).
  - **Pós-shuffle**: headers embaralhados por build, versão reportada na conexão (pacote 4000). ≥ **2011-10-05** (primeira definitiva: `RELEASE63-201110051250`; a 1ª build embaralhada é `RELEASE63-201110031118`, 03/10 11:18 — a build seguinte, `RELEASE63-201110040910`, voltou à tabela estática; deploy+rollback é leitura, não fato, os dumps são builds de dev). "R63A" é nomenclatura da comunidade para as eras pré-shuffle, não uma versão.
- **Âncora temporal**: `HabboVersion` conservadora atribuída na conexão (a última build da era detectada) até as **misc client variables** refinarem a versão exata por cliente via `flash.client.url` (o gordon URL carrega o nome da release com timestamp). Predicados temporais (`isVersionAtLeast`/`isVersionBefore`) avaliam contra a âncora.
- **Shuffle**: a fronteira em que a Sulake passou a embaralhar headers por build (2011-10-04 → 2011-10-05). Antes dela, uma tabela de header estática serve toda a era.
- **`sendResponse(outgoing, outgoingR63A, args)`**: o seam de dispatch por era na session — a decisão de qual enum enviar vive ali, não em if/else nos callers. `sendHabboResponse(Outgoing)` / `sendHabboResponse(OutgoingR63A)` são os guards tipados por era.
- **Convenção de stripId negativo**: o id de item de inventário trafega NEGATIVO nas duas eras (FurniList, AddOrUpdate, FurniListRemove). Evidência AS3: desde R62/2010-11-12 o cliente compara `selected.id == -(roomObjId)` no placement (WIRED); o AIR faz `getItemById(-id)` e `Math.abs` ao colocar. Clientes 2009–R54 não têm expectativa de sinal. Namespaces independentes ficam positivos: ids de item em trade (lista própria), ids de mobília em quarto e unit ids de bot/pet.
- **FurniListRemove (INVENTORY_REMOVE_OBJECT)**: existe desde r34/2009 (header 99, ainda Wedgie) com estrutura idêntica até hoje (2013-05: header 3556; AIR 2026): 1 int stripId → lookup pela chave exata da lista → remove do inventário. A tabela estática `HabboMessages` (id→evento) dentro de cada cliente é a fonte autoritativa de headers — mais confiável que correlação de hash do HabBit.
- **Branch temporal vs branch de era**: features datadas usam predicados temporais estritos (`isVersionAtLeast/Before/Between`); decisões de framing/roteamento de tabela usam `session.isPreShuffle`. Nunca inspecione `outgoingR63A != null` nem compare `release == "R63A"` fora do decoder.
- **Forma canônica do predicado temporal**: `habboSession.isVersionAtLeast(...)` (extensions em `HabboVersion.kt`); dentro do escopo `habboResponse.apply`, chamadas nuas (`isVersionAtLeast`, `isAir`). Nunca pule o receptor (`habboSession.habboVersion.isX`).
- **Parser temporal puro (`RoomSettingsWire`)**: a arqueologia de wire do ROOM_SAVE_SETTINGS (2009-11-13 → AIR 2026-05-18) vive em `parseRoomSettingsWire(habboRequest, version)` — uma função pura bytes→DTO, campos null = a era não envia (o applier preserva). O handler é um applier fino de política de domínio (clamps, VIP, mutação, resposta). É o padrão a seguir para incoming densos em gates temporais: o teste de era (`RoomSettingsWireTest`, bytes sintéticos por era — binário moderno e B64/VL64 Wedgie) transforma regressão de wire em falha de build, não em crash de cliente.
- **Contrato dos gêmeos de serializador (`IHabboResponseSerialize`)**: `serializeHabboResponseR63A` tem corpo default que delega ao método moderno. **Override = divergência real documentada** (hoje: `Room`, `UserItem`, `CatalogItem`, `MessengerFriend` — cada um é outro pacote/encoding de fato). Nunca escreva delegação manual; se o wire é o mesmo nas duas eras, NÃO sobrescreva. Um método só com gates temporais por campo (padrão AchievementsEvent/RoomUser) é preferível a gêmeos quando a divergência é datável.
- **Wire do UsersMessageEvent (ROOM_USERS, header pré-shuffle 28)** — evolução completa (AS3 bissecado + timeline): campos comuns `id, name, motto, figure, roomIndex, x, y, z, dir, entityType`; ramo user: `sex`, `xp` (morre entre os builds 2011-10-05 e **2011-10-17**), `groupId, groupStatus, groupName`, String extra (nasce **2011-10-05**, 1º pós-shuffle), `achievementScore` (≥ **2010-12-03**), `isModerator` Boolean (≥ **2014-01-30**; o AS3 chama isModerator — escrever hasBuildersClub ali era valor trocado), `badgesRank` Int (≥ **2026-05-18**, AIR). Ramo pet: `petType` sempre; pós-shuffle nasce `ownerId+hasSaddle` (**2011-10-05**) e cresce `isRiding` (2012-03-23), `canBreed` (2012-03-29), `canHarvest` (2012-04-11), `ownerName+rarityLevel+canRevive` (2012-04-24), `hasBreedingPermission+petLevel+petPosture` (2012-04-30). Ramo bot: **NÃO lê nada além dos comuns em nenhuma era** (2011→2026) — campos extras são corrupção que desynca o loop.
- **`WiredDialogWire`**: fonte única das datas do wire do diálogo Wired (save incoming e writeDialog outgoing consultam os mesmos fatos): diálogo AIR ≥2023-04-14; variableIds nascem **juntos no dialog e no save em 2024-05-06** (atualização do WiredContext; 2024-04-23 ainda não existem — o gate 2023-06-30 antigo era mito) e viajam como **Long** (8 bytes) até <2024-12-12 e como **String/UTF** a partir de 2024-12-12 (bissecção: readLong em 2024-07/10/11, readString em 2024-12-12; a forma Int nunca existiu); stuffIds2/defaultIntParams ≥2025-05-06; isInvert (só dialog) <2024-05-06; WiredContext/conditionTypeSpecifics ≥2024-05-06. O `isInvert` não é ecoado no save em nenhera era (caller do UpdateConditionMessageComposer 2024-01-22) — assimetria por design.

## Persistência

- **Entidade suja (`AbstractDirtyEntity`)**: entidade de estado de jogo marcada para flush; o `WriteBehindManager` coleta e invoca `flush()` polimorficamente.
- **Write-behind**: escritas JDBC deferidas para o pool `Dispatchers.IO` — JDBC síncrono nas threads do Netty é proibido.
- **Seam de write-behind nos DAOs**: `db {}`/`dbTransaction {}` são SÍNCRONOS (`jdbi.withHandle` na thread do caller) e só existem dentro do pacote `ovh.rwx.habbo.database` — a task `verifySyncJdbiAccess` (build-logic, scan de bytecode da referência inline a `Jdbi.withHandle/inTransaction`) falha o build se aparecer fora dali (whitelist: `HabboServer`, `PermissionManager.load()` — boot). Métodos de escrita de DAO chamados de handler/thread de jogo **se auto-enfileiram**: `fun deleteItems(...) = WriteBehindManager.queue { db { ... } }`, com snapshot dos valores antes de enfileirar quando a entidade é mutável. Flush garantido (logout/unload/shutdown) roda dentro do `WriteBehindManager` e usa os núcleos síncronos. **Limite conhecido**: writes que precisam do ID gerado ainda são síncronos (`createRoom`, `insertPet`, `addItems`, `addBadge`…) — a migração deles passa por alocar o ID via `HiLoSequence` antes do insert e enfileirar (padrão já provado em `MessengerDao.addFriends`, `addRequest` e `CameraDao.savePictureDataToDatabase`).
